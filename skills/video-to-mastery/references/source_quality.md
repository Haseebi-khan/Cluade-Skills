# Source Quality & Citation

## Tiering

When verifying whether something is current, prefer sources in this order:

1. **Official documentation, official repository, official specification** — the ground truth for "does this API/command/config still exist as shown"
2. **Official announcements, release notes, papers** — best for "what changed and why"
3. **Highly reputable technical sources** (well-known engineering blogs from the maintaining org, established technical publications)
4. **Community sources** (Stack Overflow, forums, third-party tutorials) — useful for context and gotchas, but not the basis for a currency claim on their own

Avoid basing an "outdated" or "current" verdict on SEO-optimized content-mill articles, unverified forum posts, or low-quality AI-generated summaries — these are exactly the kind of source that itself goes stale silently.

## Citing what you find

When you use web research to support a specific claim in the output (e.g. "this API was deprecated in version X"), make the source identifiable — name it (official docs, GitHub release notes, etc.) and link it where you have a real URL. Never invent a citation or a version number you didn't actually verify. If you can't verify something confidently, write "I could not verify this reliably" rather than presenting a guess as fact.

## When sources disagree

Don't silently pick one. Prefer the primary source (the tool's own docs/repo) over secondary commentary, but if there's a genuine live disagreement (e.g. docs recommend X, but the community has largely moved to Y for practical reasons), say so and explain both sides briefly rather than presenting only one as truth.
